# Xmouse 外部评审与迭代验收

基于 0.15.1 源码和本机发布文件审查；0.15.2 只实现 Steam 关闭兼容修复。本文件其余内容为建议排期。

## 判断

| 意见 | 判断 | 建议 |
| --- | --- | --- |
| 依赖外部 SQLite DLL，便携发布易损坏 | 成立，是可消除的交付问题 | 下一版默认静态链接 SQLite，交付一个 EXE；不要只增加“请保留 DLL”的说明 |
| 两类成熟产品夹击，脚本能力有上限 | 有产品取舍价值，但“单点永远打不过”不是可验证结论；当前主要用途仍是个人高频操作 | 明确鼠标操作流的目标用户，优先兼容性与日常完成率；先开放应用规则和自定义组合键，按真实需求决定脚本 |
| 自绘 UI 导致键盘和无障碍体验残缺 | 核心问题成立；“所有语义都要手写”过度概括了原生控件已有能力 | 下一版把键盘导航和可读状态列为发布门禁；先保留真实控件语义，再补绘制，不能只验收截图 |

## 1. SQLite：问题在交付边界，不在数据库选择

证据：`Cargo.toml` 默认 `rusqlite = "0.37"`；本机 EXE 的 PE 导入表含 `sqlite3.dll`。当前 EXE 为 1,112,064 字节，配套 DLL 为 3,290,624 字节（0.15.1）。移动整个便携目录可用，单独移动 EXE 且新位置没有可加载的 SQLite DLL 时，Windows 加载器可能在 Rust `main` 之前终止启动。更准确地说是“无法启动”，不能保证应用自己的日志或错误框有机会出现。

项目已经有 `ci-bundled-sqlite` 功能，`.github/workflows/quality.yml` 中也配置了该功能；普通便携版与 CI 构建路径目前不同。建议统一为默认 bundled 构建，移除手动配套 DLL 的发布要求，保留可选系统 SQLite 只供开发使用。`rusqlite` 的 [官方构建说明](https://github.com/rusqlite/rusqlite#notes-on-building-rusqlite-and-libsqlite3-sys) 明确支持将 SQLite 源码编译并链接进程序。

静态链接不意味着“把 3.3 MB 全部常驻内存”，也不能保证内存一定更低；磁盘体积、工作集和堆内存是不同指标。需要用相同优化参数比较 EXE、ZIP、启动耗时和空闲内存。SQLite 安全更新将随应用重新构建发布。

验收：PE 导入表不含 `sqlite3.dll`；将单独 EXE 放入有空格/中文的新目录，执行存储自检并冷启动；读取现有历史和统计、迁移、去重、置顶、DPAPI 回归通过。存储自检应在安装钩子之前退出，便于 CI 验证，不干扰真实用户会话。

## 2. 定位：先确定服务谁，再决定功能边界

“一体化 + 轻量”目前更多是工程描述，用户收益应该表达为：按住鼠标即可完成常用窗口操作、搜索和历史粘贴，且游戏中不打扰输入。个人工具的成功标准是这些操作每天可靠可用；若面向公开分发，再评估迁移成本、上手体验和与系统功能的差异。

成熟工具有更多功能并不直接证明本项目没有价值；反过来，文件小、Rust 或测试数量也不能证明体验更好。最近的松键遗留、Steam/Wallpaper UI 关闭兼容说明，当前主要短板是操作结果是否可信。`SendInput`、`PostMessage` 成功只表示提交成功；现有 `result=success` 和“调用成功”应按此解释，不能用来宣传真实动作成功率。

建议先做：

1. 应用级动作规则：同一 L 轨迹在浏览器关闭标签，在 Steam 关闭当前窗口；规则要可查看、可撤销，避免兼容例外继续散落在 `actions.rs`。
2. 自定义组合键：允许绑定有限键盘组合和明确的目标窗口，不必先引入任意脚本运行时。
3. 配置导出/导入、规则恢复默认，减少用户迁移和调试成本。
4. 对可以确认的动作记录 `submitted / confirmed / failed / unknown`，例如关闭后检查目标窗口已隐藏或销毁；不能确认的应用保留 unknown，不能自动追加另一种可能误关闭的动作。

任意脚本、插件可以是后续产品方向，但需要独立设计执行超时、取消、权限、版本兼容和支持成本。它是扩展性的选择，不是修复基本可靠性所必需的前提。本轮不建议立刻复制大型自动化平台的范围。

## 3. UI：有原生基础，但语义和导航确有缺口

代码证据：

- `ui/native.rs` 创建真实 `BUTTON`、`EDIT`、`LISTBOX`；按钮有窗口文字，历史列表使用 `LBS_HASSTRINGS`。这些通常能获得系统的基础名称和控件语义，不能认定完全没有无障碍能力。
- `app.rs::message_loop` 没有 `IsDialogMessageW` 或等价主设置页 Tab 导航。许多控件虽有 `WS_TABSTOP`，仅此不足以提供完整的对话框键盘体验。
- 历史弹窗已有 Enter、Delete、Esc 和原生列表方向键处理，所以也不是“完全无法用键盘”。但焦点切换、筛选器和动作按钮仍需整体走查。
- `ui/widgets.rs` 的按钮/开关/分段选择绘制未处理 `ODS_FOCUS`，看不到清晰键盘焦点。
- 开关和选中值保存在 `GWLP_USERDATA`，系统并不知道它等同于 checkbox/radio 的状态。界面读起来像按钮，不意味着读屏软件能获得 Toggle/Selection 状态。
- 个性化画布和统计条形图主要画在父窗口，没有专门的 UIA/可访问对象。项目中用 UI Automation 读取其他应用选区，并不等于已为自身 UI 提供完整支持。

[IsDialogMessageW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-isdialogmessagew) 也可用于包含控件的普通窗口。第一步应补齐主设置/历史的 Tab、Shift+Tab、Space、Enter、Esc，切换页面后把焦点落到可见控件；把焦点框绘制出来，并确保隐藏页面不参与 Tab 顺序。

第二步应保留或补齐 checkbox/radio/list 的语义状态：优先使用真实控件状态与可访问代理；如果继续自绘独立控件，就提供对应 UIA 模式和状态变更事件。统计页提供可聚焦的文字/列表摘要；个性化轨迹训练至少能用键盘选择手势、管理样本并取消训练，无法绘制的用户仍可使用默认轨迹。

验收应包含纯键盘完成设置保存与历史筛选/粘贴、可见焦点、Narrator/Inspect 能读出名称/角色/选中状态，以及浅深色、100%/150%/200% DPI。当前这一项应视为基础体验欠账，不能长期停留在路线图。

## 建议顺序

| 阶段 | 改动 | 交付标准 |
| --- | --- | --- |
| 本轮 0.15.2 | Steam 的 L 动作兼容 | 实体 Ctrl+W 对照；修复后 Steam 当前窗口正常关闭/收回托盘；游戏、浏览器、Wallpaper UI 不误改 |
| 下一轮 A | 单 EXE + 可自动运行的便携自检 | 消除 SQLite DLL 依赖；在全新目录验证发布件而非仅测试 Harness |
| 下一轮 B | 纯键盘与控件语义 | 按上述键盘/读屏/DPI 场景验收；保留既有低常驻目标 |
| 随后 | 应用规则和自定义组合键；动作结果分层 | 规则集中、可撤销；按键提交和实际效果不再混算 |
| 需求成熟后 | 评估脚本/插件、组件框架迁移 | 根据维护成本与真实使用需求立项，不以功能数量作为唯一标准 |

工程重构继续按已有计划抽离窗口控制器和手势状态机。框架是否替换应由键盘、UIA、DPI 的验收成本决定；仅为圆角或截图观感更换整套 UI，不会自动解决动作兼容问题。
